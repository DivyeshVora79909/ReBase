## Probe selection and local timing

Use the smallest probe that covers the changed contract. A focused module edit
gets compiler build/check, native schema validation, and its isolated module
probe. Compiler/tree edits add the affected primitive regression and dependent
module probe. Run `probe:runtime` for gateway, queue, webhook, migration, or
shared runtime changes; run all-in-one application suites at integration or
cutover. Avoid repeating an unchanged broad suite inside a module-local edit
loop. Recent local samples are 0.96 seconds for accounting build, 0.73 seconds
for compiler check, 0.29 seconds for schema validation, and 6.52 seconds for
`probe:accounting-core` at A1/A2a (8.43 seconds at A2b and 17.61 seconds with
A2c invoice coverage); the broad runtime probe previously took about 42 seconds.
These are single local samples, not performance guarantees.

## Small function-call measurement

Run without CLI options:

```bash
node dev-tools/research/redesign-probe.js
```

Or import its `functionCalls({ iterations, samples })`, `queueSemantics()`, or
`run()` functions from a JS development script. Inputs are bounded; the probe
cleans up temporary servers in `finally`. The [probe source](../../dev-tools/research/redesign-probe.js)
and [raw successful-run evidence](./redesign-evidence.json) preserve the method,
versions, every paired database/HTTP timing, and transport assertions.

| 500-iteration case | Inline DB time, median (min–max) | Function DB time, median (min–max) | Paired overhead per call, median (min–max) |
|---|---:|---:|---:|
| Decimal arithmetic | 4.439 ms (4.285–6.893) | 8.952 ms (8.658–13.674) | 8.950 µs (8.121–14.462) |
| Ordered sum/min-prefix/max-prefix fold | 19.928 ms (18.701–24.881) | 23.755 ms (22.711–30.090) | 7.352 µs (3.436–11.928) |

Use the median of paired differences; subtracting two independent medians is a
different statistic. The function path includes invocation, argument handling,
and lookup/evaluation overhead, so this does not isolate a single interpreter
mechanism. Decimal HTTP values arrived as strings; the oracle normalizes only
these bounded small fixture results, not arbitrary production decimals.

**Decision:** keep shared native functions and compile-time specialization.
Function calls are measurably nonzero overhead, especially for tiny arithmetic,
but this experiment cannot establish the main write bottleneck. First measure
complete-operation time split into derivation, routing, tree reads/writes,
validation, and retries. Inline a hotspot only if that evidence justifies the
larger generated schema and duplicate code. There is no evidence here for
rewriting the AVL because of function interpretation.

## Queue details established by the experiment

The installed BullMQ [options](../../node_modules/bullmq/dist/esm/interfaces/base-job-options.d.ts)
and [job validation](../../node_modules/bullmq/dist/esm/classes/job.js) agree with
measured behavior: zero/unset priority runs before positive priorities, lower
positive values run first, and duplicate IDs do not replace active queued data.
The public guides describe [priority](https://docs.bullmq.io/guide/jobs/prioritized),
[delay](https://docs.bullmq.io/guide/jobs/delayed), and
[job IDs](https://docs.bullmq.io/guide/jobs/job-ids).

The exploratory probe initially used the literal job ID `delayed`. That
collided with the queue's own Redis `delayed` key and produced WRONGTYPE on
this installed version. The successful fixture uses `j-` names, and the target
runtime uses a `w-` hash prefix. Never pass raw business IDs or queue key names
as custom job IDs. The first arithmetic check also exposed decimal-as-string
HTTP representation; it was corrected before recording the successful run.

Removing a missing job returned success; removing an actively locked job
returned refusal. Neither queue removal nor a version fence can undo a provider
side effect already performed. That is why the design retains durable execution
identity and uncertain-outcome reconciliation.

## Data structure decision

The workload needs arbitrary backdating/rekey/deletion, exact ordered summaries,
rank/select, bounded-height maintenance, and synchronous validation. The current
intrusive AVL fits those requirements. This comparison is algorithm analysis;
only the function/queue experiments above were timed in this pass.

| Candidate | Useful property | Cost / mismatch for this workload | Decision |
|---|---|---|---|
| Augmented AVL | Worst-case O(log n) search/update and rank/prefix/range with bounded summary algebra. | Path-summary writes, root contention, and record rewrite cost remain; multiple slots share a row's conflict boundary. | Keep as the core. Separate order/summary/domain policy from mechanics. |
| Red-black tree | Worst-case O(log n), potentially fewer structural rotations. | Summary repair still touches ancestors; different metadata and deletion rules need full proof. CPU rotation count does not establish KV improvement. | No rewrite without equivalent durable-operation measurements. |
| B/B+ tree | Higher fanout can reduce storage reads and improve range locality. | Packed-node writes, splits/merges, summary partitioning, and fanout tuning introduce new persistence tradeoffs. | Candidate only if real KV/path I/O dominates; no measured superiority here. |
| Treap | Small implementation, expected logarithmic paths. | Unbounded worst-case height and random/adversarial-priority assumptions differ from the requested deterministic guarantee. | Do not replace AVL. |
| Fenwick/segment tree | Strong sums/extrema over known coordinates; useful fixed integer domains. | Coordinate remapping or sparse-universe storage for arbitrary mutable dates/keys; distinct rank/tie semantics. | A specialized future root contract, not a universal replacement. |
| Sorted array or append-then-rebalance | Cheap append in a strictly append-only history. | Arbitrary middle edits/delete can cost O(n); deferred balance changes write bursts and guarantees. | Does not match editable history. |
| Native indexes/views | Built-in nominal grouping, lookup, ordinary ordered queries. | They do not automatically provide exact maintained arbitrary prefix minima or reactive aggregate closure. | Use for the paths they already solve; avoid unnecessary trees. |

Keep existing predecessor/successor links for ordered navigation and dependent
subtree counts for sparse reactive sweeps. A linked list alone must traverse
intervening static members; a native indexed suffix scan can also read many
irrelevant rows. For dense consumers a range stream may win constants, but that
comparison needs a representative database measurement. Do not assert that a
FOR loop or extra linked index is inherently faster.

For `r` visited dependent records, `m` average active memberships, bounded
summary width `q`, and typical tree population `n`, a conservative work model
is `O((1+r) m q log n)` plus routing/cycle checks, current coalescing
`O(m² q)`, database I/O, audit, retries, and contention. Exact materialized
changes to `r` rows require at least Ω(r) work. `m` is memberships, not DAG
depth; a root family is not a runtime instance. `n` counts actual positions.

A root guard needs O(q) summary work after maintenance; a whole write is not
O(1). No timing from this small probe or the older compressed logical-population
fixture demonstrates physical million-row capacity. Memory/storage usage and
low/normal/severe write throughput were not measured in this design pass.
